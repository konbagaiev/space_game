## 1. Goal

Today a duel happens entirely inside one tab: the browser spawns the aces, flies them, kills them or gets
killed, and the only record is a session row nobody can check. This change makes a duel **verifiable**: the
duel descriptor moves into `sim-core` so a server can rebuild the exact room, the recorded trace carries the
one parameter that defines it (`room: { kind:'duel', aces:N }`), the browser publishes a **digest of the
World at the instant the fight ended**, and the server re-simulates the submitted input trace headlessly and
compares. The result is a **verdict** — `agree` / `disagree` / `unverifiable` — written onto the
`gameplay_sessions` row and shown as a column on `/admin/sessions`.

**Nothing binds.** No credits, no XP, no progression, no gate depends on the verdict. This is DECISIONS
§129's own first cut ("the verdict is recorded before it is allowed to bind"), and the reward model is
deliberately deferred by the maintainer. The user-visible effect for a *player* is exactly zero; the
user-visible effect for the *maintainer* is a column on the admin page that says whether the server and the
browser simulated the same fight.

Why the duel is the right first subject, where the campaign was not: a duel is **short** (seconds to a
couple of minutes, so drift has no room to compound — §129 measured that every run that agreed was ≤4 kills),
it is fought on **the build that served the page**, `withDuelRoom` drops `lastKillDrop` so the
account-state-dependent `ownsReward` branch is never reached (see §3.3), and it pays nothing, so a wrong
verdict cannot rob anybody even by accident.

## 3. The three things that make this work

### 3.1 The anchor: digest the end of the FIGHT, not the end of the trace

A duel ends twice, exactly as every mission does (DECISIONS §130). The arena empties → 1.5 s later the
`victory` phase fires `clearMission` → `levelRunner.cleared = true` and the reward is decided. Only *then*
does the player press "Finish and Return", fly home and dock, and only docking sets `levelRunner.won`.

**That button and that dock are not in the input trace.** A trace records keys and touch, never a mouse
click (DECISIONS §129: "a headless referee can never win"). So at the end of a *winning* duel the client's
World carries `won`, `finishing`, `returningToBase`, `world.returnToBase` and an engaged `autopilot` — and
the referee's World carries none of them. Every one of those fields is inside `worldDigest`
(`client/src/sim-core/digest.js`, the `lr` and `ap` parts). Digesting the final state would therefore mark
**every honest winning duel `disagree`**, 100% of the time.

`cleared` and death are different: both are decided inside `sim-core` as a pure consequence of the fight,
with nobody clicking anything, so a browser, a room and a headless referee all reach them identically. That
is the anchor:

```js
// client/src/sim-core/duel-config.js
export const duelAnchorReached = (world) =>
  !!(world.levelRunner.cleared || !world.player.alive);
```

Both hosts take the digest at the **end of the sim tick** at which the predicate first holds, which is the
same instant on both sides:

- **Node** — `runTrace()` evaluates a new `stopWhen(world, i)` option after `simTick`, and breaks. The
  digest `runTrace` already computes after the loop is then the anchor digest, and `ticksRun` is the anchor
  tick. (`!player.alive` already breaks there today; `cleared` is the case that needs the new option.)
- **Browser** — `renderTick` drains the sim events *after* `simTick` has fully run (`client/src/sim.js:525`,
  inside `update()`), and both `cleared` and `death` handlers call `G.flushSession(...)`. So sealing the
  anchor at the **top of `flushSession`** captures the World at exactly the end-of-tick state, from inside
  the very tick that ended the fight. Presentation (`renderTick`) never writes simulation state
  (DECISIONS §117), so there is nothing between the two hosts' observation points.

#### 3.1a The off-by-one this exposed — a real, pre-existing bug in ALL session recording

`stepReplayTick` (`client/src/replay.js:253`) calls `capture()` **after** `update(dt)`. But `update(dt)`
drains the events, and the `cleared`/`death` handlers call `flushSession` — which builds and uploads the
trace **before this tick has been captured**. So today:

> **every recorded session's uploaded trace is missing its final tick** — the tick on which the level was
> cleared, or the player died.

For the referee this is fatal, not cosmetic: the trace runs out one tick short of the anchor, the referee
never reaches `cleared`, and every honest cleared duel reports `no-anchor`. (It is very likely also part of
why the 2026-08-21 campaign survey measured 20% agreement: `verifyRun` returns `win-not-earned` for a
claimed win whose re-simulation never set `cleared` — which is precisely what a trace missing its last tick
produces. **We are not re-opening campaign verification here** — just noting the cause.)

**The fix is one line: move `capture()` to just before `update(dt)`.** It is content-neutral — nothing in
`sim-core` writes `world.input.keys` or `touchAim` (verified: `step-player.js` and `steering.js` only read
them), so the snapshot is identical taken before or after the tick — and it makes the trace contain the
tick during which the fight ended. This is a bug fix, so §7.1 specifies both its regression test and the
one existing assertion (`client/src/replay.test.js:269`) that this inversion requires editing.

### 3.2 The engine column: what an honest `disagree` can still be

After the anchor fix and the build gate, the remaining way an **honest** player produces a `disagree` is a
cross-engine floating-point difference. `Math.sin`, `Math.atan2`, `Math.hypot` and `Math.pow` are
implementation-defined in ECMAScript, and `36-sim-divergence` only proves **Chromium ↔ Node**. Nothing in
the project has ever compared WebKit or Gecko against Node.

Without the engine recorded, the first `disagree` is uninterpretable: a cheat, a sim bug, or just Safari?
So every session POST carries the engine **family + version** — a technical fact about the machine that ran
the simulation, not the User-Agent and not a trace of the player.

### 3.3 Why the strict digest oracle is legitimate here

§129 says plainly that "the world digest is the wrong oracle for money", because the last kill's reward drop
is gated on `ownsReward`, which reads account state a trace does not carry and whose two branches consume a
different number of RNG draws. **That branch cannot be reached in a duel.** `withDuelRoom` drops
`lastKillDrop` from the descriptor, and `step-enemies.js:171` reads

```js
if (lkd && isLastKillDrop(...) && !ownsReward(world, lkd)) { … } else if (simRandom() < DROP_CHANCE) { … }
```

`lkd` is `undefined` → JS short-circuits → `ownsReward` is never called and the kill falls through to a
single seeded `simRandom()` draw. The duel's loot roll is therefore fully deterministic from the seed, and
the digest is a sound oracle for a duel specifically. Say this in the code comment, not just here — the next
reader will arrive holding §129.

The standing proof that cross-host bit-identity is achievable at all is `36-sim-divergence`, which already
requires a real browser and Node to agree on the **full-precision digest AND the draw count** for the
canonical Level-0 trace (`hash=0x8d802ca2`, `draws=38`). This feature is that guard, applied to a live duel
instead of a recorded intro.

### S11 — `server/src/seal/verify-duel.js` (new)

Sibling of `verify-run.js`, reusing its `classifyTrace` for the shared admission rules (v4+, not truncated,
a catalog level, the claim's level matches, the build gate).

```js
export const DUEL_VERIFY_MAX_TICKS = 12000;   // ~3.3 min of duel. Past that we refuse rather than block the loop.

export function classifyDuel(trace, claim, { build = null } = {}) {
  const why = classifyTrace(trace, claim, { build });        // v4 / truncated / unknown-level / build-drift …
  if (why) return why;
  const room = trace.room;
  if (!room || room.kind !== 'duel') return 'not-a-duel';
  if (!Number.isInteger(room.aces) || room.aces < 1 || room.aces > ACE_COUNT_MAX) return 'bad-room';
  if (!claim.anchor || !Number.isInteger(claim.anchor.tick) || claim.anchor.tick <= 0) return 'no-anchor-claim';
  if (traceTickCount(trace) > DUEL_VERIFY_MAX_TICKS) return 'too-long';
  return null;
}

// Judge one duel. Returns { verdict, note, ticksRun, hash, draws } — verdict ∈ agree|disagree|unverifiable|error.
export async function verifyDuel({ trace, claim = {}, build = null, run = runTrace } = {}) { … }
```

The comparison, in order (each produces a `note` a human can read off the admin page):

1. run with `stopWhen: duelAnchorReached`;
2. **the referee never settled** (`!duelAnchorReached(r.world)`) → `disagree`, note
   `no-anchor (ran N/M ticks, kills=K hp=H)`. This is the loudest signal the mechanism can produce: the
   input the player uploaded does not end the fight it claims to have ended;
3. `r.ticksRun !== claim.anchor.tick` → `disagree`, note `tick <sim>≠<claim>`;
4. `r.draws !== claim.anchor.draws` → `disagree`, note `draws <sim>≠<claim>` **first**, before the hash: a
   draw-count mismatch names the culprit (something drew from the seeded gameplay stream on one host and
   not the other — DECISIONS §73), where a hash mismatch only says "different";
5. `r.hash !== claim.anchor.hash` → `disagree`, note `hash 0x…≠0x…`;
6. otherwise `agree`, note `kills=K hp=H t=<ticks>`.

Refusals return `{ verdict: 'unverifiable', note: <the classify reason> }`; a throw returns
`{ verdict: 'error', note: String(e && e.message).slice(0, 200) }`.

The header must state, in the same plain voice as `verify-run.js`: **this module decides nothing**, no
caller may bind money to it until the honest-player disagreement rate has been measured (§129), and the
§3.3 reason the digest is a sound oracle for a duel where §129 says it is the wrong one for money.

Also export the orchestrator the route uses, so it is testable without HTTP:

```js
// Verify + persist. `save({ id, verdict, note })` is injected (db.recordSessionVerdict in production).
export async function verifyDuelSession({ id, trace, claim, build, save }) { … }
```
It logs one line — `[referee] duel <id> <verdict> (<note>) in <ms> ms` — so the cost of the re-simulation is
measured rather than assumed, and the measured figure goes into SUMMARY.

**One property to preserve deliberately: the referee does NOT require the trace to end at the anchor.** It
stops when the fight settles and ignores whatever input follows. In production the two coincide (the
`cleared`/`death` event closes the recorder in the same tick), but a trace that carries extra ticks — a
provisional upload, a future flow that keeps recording the flight home — must still verify. Never derive the
stop point from `claim.anchor.tick`: the referee has to find the anchor itself, or the client is grading its
own homework.

`classifyDuel` needs `traceTickCount` from `client/src/replay.js` and `ACE_COUNT_MAX` from
`client/src/sim-core/ace.js`, alongside `classifyTrace` from `./verify-run.js`.

## 5. What a `disagree` MEANS to whoever reads /admin/sessions

Put this paragraph in SUMMARY as well, verbatim in spirit:

> A verdict says whether **this server, running this build, re-simulating the input the browser uploaded,
> ended up in the same world state at the same tick**. `agree` means the two hosts simulated the same fight.
> `disagree` means they did not — and in order of likelihood that is: (1) a bug in the simulation or in this
> mechanism; (2) a **cross-engine floating-point difference**, which is why the JS engine is recorded next
> to it (§3.2) — `36-sim-divergence` only proves Chromium ↔ Node, and nothing has ever proved WebKit or
> Gecko; (3) a build the gate failed to catch; and only then (4) someone tampering with a trace that pays
> nothing. **Nothing may bind money, XP or progression to a verdict until the disagreement rate on honest
> players has been measured** — that is DECISIONS §129's own rule, written after a survey of 74 production
> sessions found 20% agreement and not one cheat. The reward model for duels is deliberately deferred.

## 6. Replay / intro impact

**Nothing in this change consumes, moves or reorders a seeded draw.** `worldDigest` only *reads*
`simRandomDraws()`; `duelAnchorReached` reads two booleans; the `stopWhen` option only ends a loop earlier;
`withDuelRoom` moved file but not a line of behaviour; `sim-host`'s new `duel` hop is inert unless a trace
carries a room. `duelBuild` in `beginLiveSession` is a no-op with the flag off, and it changes *what is
written into a trace*, never what the sim does.

The one behavioural change on the shared path is S4's `capture()` move, which affects **recording only**:
playback applies input before `update()` exactly as it always has, and `capture` is a no-op under
`?playback`. Existing recorded traces — the Level-0 intro asset above all — are untouched bytes and replay
identically.

**How the plan proves it:**
- `cd server && node --test tools/sim-replay.test.js` — the canonical Level-0 trace still replays
  bit-identically (3490/3490 ticks, 4 kills, 125 credits).
- `cd client && node visual/run.mjs 22-intro-replay` — the intro cutscene still reaches 4 kills, p0..p4 and
  a win in a real browser.
- `cd client && node visual/run.mjs 36-sim-divergence` — browser and Node still agree on
  `hash=0x8d802ca2` / `draws=38`. This is also the guard that S10's new option did not disturb the default
  stop condition.

## 9. Out of scope / non-goals

- **Any reward, payout, gate or enforcement.** The verdict changes no balance, no XP, no progression, and no
  caller may read it to decide anything. Deferred by the maintainer, and required by §129.
- **A player-facing duel entry.** `?duel` stays a dev flag; no menu button, no UI, no verdict shown in game.
- **Campaign verification.** `verifyRun` still writes nothing and no campaign row gets a verdict, even
  though §3.1a's fix probably improves its numbers. Re-measuring the campaign survey is a separate slice.
- **`?beam`'s recording hole.** `beamLoadout` has the same "the trace records the account's gear, not the
  gear that was flown" problem as `duelBuild` did. Fixing it is a one-liner but it is a different flag with
  different tests; name it in SUMMARY as known, do not fix it here.
- **Forwarding `?duel` over the netsim handshake.** S1/S3 remove the *blocker*, not the feature. Do not add
  the handshake hop.
- **Suppressing the duel's loot drop.** `docs/plans/duel-room.md` §8 already documents that an ace's death
  rolls the ordinary 20% drop; that roll is exactly what makes the fight deterministic (§3.3). Leave it.
- **Any new column, table, dashboard or sweeper beyond the three columns in S13.** No verdict history, no
  aggregate page, no retry queue. DECISIONS §30.
