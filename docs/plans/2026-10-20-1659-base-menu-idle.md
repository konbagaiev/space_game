# One way into the base menu: the fight stops when you're back at base

**Status:** planned. **Date:** 2026-10-20. **Feature id:** `2026-10-20-1659-base-menu-idle`.
**Scope:** Phase 1 ONLY of [`2026-10-20-base-menu-state-and-drift-fixes.md`](2026-10-20-base-menu-state-and-drift-fixes.md)
(audit finding A6 of [`2026-10-20-duplication-audit.md`](2026-10-20-duplication-audit.md)). Phases 2–5 of that
file are out of scope — see *Out of scope*.

All line numbers below were checked against this worktree (cut from `main` at `ba551a4`). They will drift as
you edit; the quoted code is the anchor.

## Goal

Reported from prod: you die inside the zone on the research-station side mission, press **Back to base** on
the death overlay, open Loadout, and the fight carries on behind the Main Window: the "You've left the
battlefield" banner, enemies spawning, and eventually a warp back into the fight. The cause is a flag leak.
"Back to base" (`client/src/mainwindow.js:126`) never clears `G.gameStarted`/`G.roam`. Then any Loadout
action (`shop.js` `applyShopState`, `:478-484` → `buildPlayerFor`) builds a fresh **alive** `G.player`, so
`update()`'s gate (`client/src/sim.js:576`, `if (!G.gameStarted || !G.player.alive || levelRunner.won) return;`)
opens and the sim ticks under the menu. The victory **Continue** path, login, and the intro landing reach the
menu the same way.

The code already assumes an invariant (bootstrap comment `client/src/main.js:2294`: "update() doesn't run
until take-off"). **While the Main Window or Welcome is up, `G.gameStarted === false` and
`G.roam === false`.** Today six entry points each uphold it by hand, or forget to. The fix makes "a menu
is open" a single transition, `enterMenu()`, that every entry point goes through. Its mirror, `leaveMenu()`,
replaces the four hand-kept copies of the menu teardown. A new visual scenario is the guard. It is seen to
FAIL on the current code first.

User-visible effect: after Back to base, Continue, login, or skipping the intro, nothing flies, spawns,
warps or shows a banner behind the menu, whatever you do in Loadout.

## Decisions (settled — do not re-ask)

1. **Keep the Welcome screen.** It is the fallback landing for a level without a briefing. Today every
   campaign level 1–4 has a briefing, so it's rarely reached. Only route it through `enterMenu()` /
   `leaveMenu()`. Deleting it is an onboarding-flow call, out of scope.
2. **Welcome's Take off keeps launching straight into the fight** (`beginLiveSession()` + `reset()`). It does
   NOT go through `launchCampaign()`'s travel-through-roam. Fix only its real drift: route it through
   `leaveMenu()`, add the missing `G.activeMission = null; G.pendingBriefing = null;`, and add the launch
   gate. Record the direct-vs-roam launch difference as a **known drift** under A6 in the audit file (see
   *Docs*).
3. **Welcome's launch gate = the existing `canTakeOff()`.** It lives in `client/src/mainwindow.js:335-338`;
   export it **unchanged**. No `canLaunch`, no `shop.js` changes. That's Phase 2's job.
4. **`enterMenu()` also unpauses** (`setPaused(false)` when `G.paused`), as `skipIntro` already does at
   `main.js:2026`. A pause must never carry from the menu into the next take-off.
5. **`skipIntro`'s hand copy is folded into `enterMenu()`.** Note: `skipIntro` must still stop the sim
   **immediately**. `finishIntro()` awaits `unlockNextLevel()` before it reaches `showMain`, and the intro
   fight would keep ticking during that await. So `skipIntro` calls `enterMenu()` in place of its hand copy.
   `showMain` later calls it again, so `enterMenu()` **must be idempotent**.
6. **`enterMenu` / `leaveMenu` live in `mainwindow.js`** and are exported. `welcome.js` → `mainwindow.js`
   closes a cycle (`mainwindow.js` already imports `welcome.js`, and `welcome.js` already imports `main.js`).
   That's the same shape as the existing between-battles cycle, which ESM resolves because every edge fires
   on a click, not at module init. Only if the page boot throws a TDZ/"cannot access before initialization"
   error, move both helpers (plus `canTakeOff`) to a new `client/src/menu-state.js` that both import.
7. **Deliberate behaviour change for netsim.** `main.js:1049` says "`G.gameStarted` stays true between
   fights, so it cannot be the gate." After this change it does NOT stay true: it is false on every menu.
   This is safe. A room's run is keyed to `G.gameStartTime` (`netRunAt`, `main.js:1170`), not to
   `gameStarted`, and `fightLive` (`:1189`) going false in the menu is exactly the "room must not keep
   stepping in the hangar" exit that comment block wants. The map overlay and dock "return to hangar" paths
   already clear it today. **Update that comment** to say so (see step 7). No netsim logic changes.
8. **The guard is visual scenario `53-base-menu-idle`, not a node unit test.** Nothing here is
   node-loadable (`mainwindow.js` imports THREE-bound modules). A pure "clears the flags" helper would only
   test itself. The bug was that callers didn't call the shared step, and only an end-to-end scenario
   observes that. The scenario must be run on the **unfixed** code first and seen to fail (*Tests*).

## Steps

### 1. `enterMenu()` — `client/src/mainwindow.js`, just above `export function showMain` (`:48`)

```js
// THE one transition into the base menu (Main Window or Welcome). Every way back to the base goes through
// here — Back to base, Continue after a win, the map's / dock's "return to hangar", login, skipping the
// intro — so "a menu is open" can never coexist with a running fight. update() early-returns on
// !G.gameStarted, so nothing ticks behind the menu even after a Loadout action rebuilds an alive G.player.
// Idempotent: skipIntro calls it at once (the intro must stop before finishIntro's await), showMain again.
export function enterMenu() {
  G.gameStarted = false;
  G.roam = false;
  G.returnToBase = false;            // the post-clear flight home is over — no return hint / clickable station
  G.missionZone = null;              // a roam-armed campaign zone must not count down from the menu
  G.autopilot.active = false; G.autopilot.target = null; // LOCAL world, deliberately not sim.js cancelAutopilot (that routes to a room)
  if (G.paused) setPaused(false);    // a pause never carries from the menu into the next take-off
  el.overlay.style.display = 'none';
  el.oobWarn.style.display = 'none'; // DOM state: don't leave a stale inline 'block' for the next frame to fix
  document.body.classList.add('menu');
}
```

Notes for the implementer:
- `G.roam`, `G.returnToBase`, `G.missionZone`, `G.autopilot` are World aliases (`client/src/state.js:173-176`).
  Writing them is fine: no sim is running and the next launch's `reset()` re-initialises them.
- `G.returnToBase` IS needed. A death on the flight home after a clear (DECISIONS §130) leaves it `true`. With
  an alive rebuilt ship, `updateReturnHint` (`sim.js:125-127`) and `stationClickable` (`main.js:592-593`) would
  otherwise read it in the menu.
- Do **not** clear `G.activeMission`, `G.pendingBriefing` or `G.roamMission`. The launchers set the first two
  themselves. `G.pendingBriefing` is read by `leaveOverlay` *before* it calls `showMain`. `G.roamMission` is
  rewritten by `enterRoam`.
- Add `setPaused` to the existing `./sim.js` import on `mainwindow.js:20`. `el` already imports from
  `./dom.js` and has `oobWarn` (`dom.js:49`).

### 5. `leaveMenu()` — `mainwindow.js`, next to `enterMenu`

```js
// THE mirror of enterMenu: tear the base menu down before a launch. Callers are click handlers (except
// launchCampaign's engage branch, which already called requestFullscreen outside a gesture before this
// change — a no-op there). Each launcher keeps its own specifics (G.activeMission, G.pendingBriefing,
// G.gameStarted/G.roam, beginLiveSession, reset) in its existing order.
export function leaveMenu() {
  if (Device.hasTouch) requestFullscreen(); // must stay inside the click gesture
  mainEl.classList.remove('on');
  document.getElementById('welcome').style.display = 'none';
  stopLoadoutPreview();
  settleBriefingReveal();                   // stop a stray timer/rAF from toggling classes after close
```

### New guard — `client/visual/scenarios/53-base-menu-idle.mjs` (`export const name = '53-base-menu-idle'`)

Precedents: `10-mission-board.mjs` (advance via `POST /api/players/:id/advance`, reload, wait for
`#mainwin.on`) and `05-hangar-shop.mjs:207-229` (take off → die → Back to Hangar). The `__game` hooks used all
exist: `gameStarted` (`main.js:1480`), `roam` (`:1583`), `combatElapsed`/`enemyCount` (`:1478-1479`),
`oobWarnVisible` (`:1534`, which reads the **inline** `display`, so it catches the leak even though
`body.menu #oob-warn` hides it by CSS), `missionZone` (`:1516`), `stepSim` (`:1562`, which calls `update()`
directly, so it ignores pause), `setPaused` (`:1485`), `levelRunner` (`:1454`, with writable fields), `player`.

**About pause in this scenario.** `setPaused(true)` stops the LIVE accumulator from stepping
(`main.js:1248`, gated on `!G.paused`). But **`reset()` unpauses** (`client/src/sim.js:790`,
`setPaused(false); // a fresh run always starts unpaused`), and both `enterRoam` and the engage
(`launchCampaign({ engage: true })`) call `reset()`. So any pause set before a Take off click is gone by the
time the fight runs, and the real rAF loop then steps alongside `stepSim`. The steps below re-pause
**after the last `reset()`** wherever determinism or the pause assertion depends on it. Don't treat
`stepSim` as the only driver unless the scenario has just re-paused.

**The runner shares one player per worker page** (`visual/run.mjs:98-110`), so the scenario must not assume
the starting level. Steps:

1. **Reach a shop-unlocked campaign level, with the campaign active.** Set `localStorage.accountPrompted = '1'`
   (defensive: it stops the one-time account prompt, `account.js:152-158`, from intercepting Continue in
   step 6). Read `GET /api/players/:pid/level` → `name` (`level-N`). While `N < 2`, `POST …/advance`.
   `SHOP_MIN_LEVEL` is `'level-2'` (`server/src/db.js:27`), which is what shows `#back-hangar`. **Then reset the
   active mission to the campaign:** `POST /api/players/:pid/missions/activate` with JSON body
   `{"missionId": null}` (`server/src/server.js:296`, `allowNull: true`). The worker's shared player may still
   have a side mission active from `10-mission-board`, and with one active `enterRoam` arms **no** campaign
   zone (`mainwindow.js:542-544`). Only then reload, and wait for `__game.player` and `#mainwin.on`.
2. **Take off into the real fight.** Click `#mw-takeoff` and wait for `__game.roam === true` (`enterRoam` is
   async). Immediately `__game.setPaused(true)`. `enterRoam`'s `reset()` unpaused, so this pause keeps the
   live loop out while the countdown is stepped. Assert `__game.missionZone` is non-null (precondition: the
   campaign is the active mission). Put the ship in the zone with
   `player.pos.set(zone.center.x, 0.6, zone.center.z); player.vel.set(0,0,0)`, then `stepSim(1)` in a loop
   (cap 400) until `roam === false`. The countdown is `MISSION_ZONE_COUNTDOWN = 3` s = 180 ticks
   (`sim-core/level-sim.js:46`). The engage's `reset()` unpauses again, so call `__game.setPaused(true)` once
   more, then `stepSim(60)`. Assert `gameStarted === true`, `roam === false`.
3. **Die → Back to base.** `player.hp = 0; player._shieldValue = 0; stepSim(5)`. Assert `#overlay` is
   displayed and `#back-hangar` is displayed. Click `#back-hangar`, then wait for `#mainwin.on`.
   **Assert:** `gameStarted === false`, `roam === false`, `oobWarnVisible === false`, `body.menu` present.
4. **Loadout action rebuilds an alive ship.** Click `.mw-item[data-mw="loadout"]` and wait for
   `#loadout-slots .slot-chip`. Store `window.__deadShip = __game.player`. Click a chip for an **optional,
   filled** slot: the first `.slot-chip:not(.empty)` whose `data-slot` is NOT `hull`/`engine`/`thruster`
   (`REQUIRED_SLOTS`, `client/src/shop.js:29`; prefer `grab`). Then click `[data-act="unequip"]` and wait
   until `__game.player !== window.__deadShip`. Assert `player.alive === true`. This precondition is what
   opened the old leak. If no optional slot is filled, fail with a clear message rather than skipping.
   **Before clicking unequip, record the item** so it can be restored in step 8: the selected chip's slot
   panel row carries the item's `data-kind` / `data-ref-id` (the same attributes `shop.js:567-569` reads for
   `equip`). If they aren't on the unequip button, read them from `__game.activeShip` (the equipped
   component/weapon in that slot).
5. **Nothing ticks behind the menu.** `const t0 = combatElapsed, e0 = enemyCount; stepSim(600);`
   **Assert:** `combatElapsed === t0`, `enemyCount === e0`, `oobWarnVisible === false`, `gameStarted === false`.
   Also assert `mainwin` still has `on` (the menu wasn't torn down by a hidden zone countdown).
6. **Victory Continue path.** Click `.mw-item[data-mw="missions"]`, then repeat step 2 exactly (take off,
   wait for roam, pause, step through the countdown, **re-pause after the engage `reset()`**, `stepSim(60)`).
   **Precondition assert:** `document.body.classList.contains('paused') === true`. Without it, the unpause
   assertion below would pass on today's code just because `reset()` already unpaused. Then

   `document.body.classList.contains('paused') === false` (only `enterMenu` can have cleared it now), and
   `body.menu` is present.
7. `shot('menu-idle')` after step 5. Expect zero page errors (the runner already reports them).
8. **Leave the shared worker player as found.** Re-equip the item removed in step 4:
   `POST /api/players/:pid/equip` with `{ kind, refId }` (`server/src/server.js:318`; the same body
